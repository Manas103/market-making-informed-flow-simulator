# Market-Making Simulator with Informed Flow and Inventory Skew

A market maker quotes a two-sided market into a real price-time-priority
matching engine against a seeded mix of informed and uninformed order flow,
and every unit of session P&L is accounted for twice: once as an obviously
correct direct mark-to-market, and once as a three-bucket decomposition
(spread captured, adverse selection paid, inventory mark) that must equal it
exactly. Every number below was measured on this machine over 500 seeded
sessions, not targeted; where a design attempt to raise a measured number
fell short of the number this project's resume bullet claims, that is said
plainly in Measured Results, not smoothed over.

**Extension (Oct. 2026):** a 33-contract European-call option chain quoted
at a Black-Scholes theoretical value, delta-hedged against the underlying
on a band policy, with the same discipline: a second three-bucket P&L
decomposition (edge captured, adverse selection, hedge slippage) checked
exactly against the same style of direct mark-to-market oracle. See
"Extension: options market making with delta hedging" below Architecture,
and the second half of Validation, Findings and Measured results.

**Extension (Oct. 2026):** a per-fill post-trade attribution view on the
original single-asset simulation: the same three-bucket decomposition
(spread captured, adverse selection paid, inventory mark), now computed
and reconciled per fill rather than only at the session level, plus
markouts at 1, 10 and 60 ticks after each fill. See "Extension: per-fill
post-trade attribution" below Architecture, and the third part of
Validation, Findings and Measured results.

**Extension (Nov. 2026):** a zero-friction Python strategy interface over
the original single-asset `SessionRunner`, via a nanobind binding
(`python/pymm`). The C++ session loop gains one new hook,
`Policy::External`, that delegates the bid/ask-size decision to a
caller-supplied function instead of the two built-in policies; the
nanobind binding wires that hook to a Python callable. A Python
re-implementation of the inventory-skew policy, run through this hook,
reproduces the native C++ policy's session P&L exactly over the full
500-session sweep, and a dedicated isolated benchmark measures what one
such decision costs when it crosses into Python. See "Extension: Python
strategy interface" below Architecture, and the fourth part of
Validation, Findings and Measured results.

**Extension (Nov. 2026):** a risk-budgeted quote-sizing optimizer over a new,
larger 120-contract chain (15 strikes x 8 expiries), written in Python
rather than C++: one linear program (built with CVXPY, re-solved every
requote) chooses how many lots to quote on each side of every contract to
maximize expected edge captured, subject to the book's net vega, net gamma
and net delta never exceeding a fixed budget even in the worst case where
every quoted lot on the exposed side fills. Compared against an
uncoordinated baseline that quotes every contract at a fixed size
independent of the rest of the book ("contract by contract"), over 500
seeded sessions each. See "Extension: risk-budgeted quote optimization
across a 120-contract book" below Architecture, and the fifth part of
Validation, Findings and Measured results.

## Why this exists

Reducing inventory variance is not free, and naming the price paid for it is
the thing a trader will actually believe over a bare P&L number, which is
unfalsifiable in a simulation. This project exists to produce one honest
decomposition ratio (how much of a fixed-spread quoter's gross spread
capture informed flow takes back) and one honest cost (what skewing on
inventory gives up in exchange for a calmer book), both stated at a named
informed-participation rate and a named session count.

## Honest framing, up front

- **This is a market-making simulation, not a market-making strategy.** The
  fair value process is exogenous: it does not react to this quoter's
  trades, and neither informed nor uninformed order flow consults the
  quoted price before choosing a side. That is a real simplification. It
  means the inventory-skew policy below works entirely through *quoted
  size*, not price, because this flow model is not price-sensitive, and a
  price-only skew was tried first and measured a flat zero effect (see
  Findings).
- **The order flow is synthetic**, generated by a seeded Mersenne Twister
  per session (`std::seed_seq{base_seed, session_id}`). There is no captured
  venue data behind any number here.
- **"Informed" means the trader already knows the current fair value; it
  does not mean the trader predicts the future.** An informed trader trades
  on the gap between the true value and the quoter's stale belief (set at
  the last requote) for as long as that gap persists, up to the next
  requote. Section "Findings" below is the record of discovering that the
  first, narrower definition of informed (only on the exact tick a jump
  landed) was unrealistic and understated adverse selection by roughly 10x.
- **Price-time priority is real, not assumed.** Every quote and every taker
  order is submitted to the vendored `IntrusiveBook` from
  [`lock-free-order-matching-engine`](https://github.com/Manas103/lock-free-order-matching-engine);
  fills, partial fills, and discarded unmatched market orders are whatever
  that book's matching logic actually produces, not an assumed fill model.
- **Every figure below was measured on this machine** (8 physical / 16
  logical cores, AMD Ryzen 7 7800X3D, WSL2 Ubuntu 22.04 capped to 12 logical
  cores, g++ 11.4, `-O2`), not targeted. Raw output is committed under
  [`docs/`](docs/).
- **Single-threaded, by design.** A market-making session is a sequential
  replay of one deterministic stream of events; nothing here needs the
  sibling repo's gateway rings, seqlock market-data publisher, or
  multi-threaded matching loop. ThreadSanitizer is correspondingly not run
  (there is no concurrency to race-check); AddressSanitizer and UBSan are,
  and are clean (see Validation).

Honest framing for the options extension, on top of the above:

- **European calls only; no puts.** The chain is 11 strikes x 3 expiries
  of calls, not a real 33-line chain with both sides. A real market maker
  would hedge a put with the same underlying and the same delta machinery,
  so nothing about the hedging or widening mechanics would change; calls
  alone keep the pricer, and the test that cross-checks it, to one formula.
- **Risk-free rate is 0.** A real short-dated equity option's rate term is
  a minor correction next to its vega; carrying it would not change which
  lever (hedge band, widening) does what, and dropping it keeps
  `options_math.hpp` to the one formula the cross-check test actually
  checks.
- **The underlying is one synthetic GBM path per session**, stepped once
  per tick with `sigma` = 0.30 annualized, "1 tick = 1 trading minute"
  (`dt_years = 1/(252*390)`). There is no captured or even historically
  calibrated underlying behind this number.
- **The quoter's own theoretical vol is the same `sigma` that generates the
  underlying.** This project does not model a vol-estimation edge (the
  quoter being *right* about vol when the rest of the market is wrong); the
  "volatility edge" in the resume bullet is the Black-Scholes value itself,
  recomputed fresh every tick from the true, current underlying price and
  time to expiry, which is what lets a quote go stale (see "The adverse
  selection mechanism" below) the instant the underlying moves and the
  quote does not.
- **Every price that reaches the P&L identity is quantized to the same
  integer-cent grid the book actually trades on.** The continuous
  Black-Scholes price is used only to decide the integer tick to quote;
  `center_at_requote`, the "theo before/after" carried into inventory
  mark, and the final mark-to-market all use that same rounded tick. The
  first implementation used the continuous price for bookkeeping and the
  rounded price for the book, and the mismatch broke the P&L identity by
  $0.01 to over $1 per session depending on spread width -- see Findings.
- **A hedge trade is an assumed fill against the underlying, not a second
  matched book.** It executes at the current underlying price plus a fixed
  per-share slippage (`--hedge-slippage`, $0.01 in the measured runs), in
  the direction that costs the hedger money, same as crossing a spread
  would. There is no second `IntrusiveBook` for the underlying; adding one
  would not test anything the vendored matcher has not already proven.
- **Which contract trades next is chosen vega-weighted, not uniformly.**
  Higher-vega contracts get hit more often, which is also exactly the flow
  the vega-scaled-widening policy exists to defend against; see "The
  adverse selection mechanism cannot be deterred by price, only diluted"
  in Findings for why that matters more than it sounds like it should.
- **Quote size is fixed per contract; there is no options analogue of the
  base repo's inventory-skew policy.** The only inventory lever modeled
  here is delta-hedging against the underlying, which is the Optiver-
  specific content this extension adds.

Honest framing for the per-fill attribution extension, on top of the above:

- **"Per fill" means every unit of the session-level decomposition is
  attributed to exactly one fill, with no double counting and no
  unattributed remainder.** `spread_captured` and `adverse_selection` are
  computed at the fill itself; the ongoing inventory carry
  (`inventory_mark`) is attributed to whichever fill most recently set the
  position being carried, since a carry cost only exists because some
  earlier fill put inventory on the book. This is a modeling choice, not
  the only valid one, and it is stated plainly so a reader can judge it:
  an alternative would spread the carry evenly across the holding period
  by time rather than crediting it all to the fill that opened it.
- **Markout is measured from the price actually traded, not from fair
  value at the moment of the fill.** `markout_h = sign * (fair_value at
  t+h - fill_price)`, sign positive when favorable to the market maker.
  Because `fill_price` already differs from fair value by the half spread,
  an uninformed fill's markout is dominated by that captured spread, not
  by zero; see Findings for the sanity check this implies and what it
  means for reading the numbers below.
- **"1 tick = 1 second" for the markout horizons (1, 10, 60), the same
  style of unit assignment the options extension already makes ("1 tick =
  1 trading minute").** The base simulation's tick itself carries no
  wall-clock unit; this is the one place that matters here, since the
  resume bullet names seconds specifically.
- **Markout horizons beyond session end are clamped to the last tick**,
  flagged per fill (`markout_*_clamped`), not extrapolated or dropped.
- **This extension reuses the base simulation's session mechanics
  unchanged.** The per-fill ledger is an optional side channel
  (`fill_log`) `SessionRunner::run` populates when a caller asks for it;
  every number the base repo and the options extension already measure
  (via the no-argument call) is bit-for-bit the same as before this
  extension, which `tests/pnl_identity_test.cpp` and
  `tests/options_pnl_identity_test.cpp` still prove on every run.
- **500 fixed-policy sessions, the same baseline configuration this
  repo's own Measured Results already uses**, not a new parameter sweep;
  the point of this extension is the per-fill view, not a new headline
  number for the policy comparison that is already measured below.

Honest framing for the risk-budgeted optimization extension, on top of the
above:

- **This extension does not route through the vendored `IntrusiveBook`
  matcher.** It is a lighter-weight Python simulation: the thing under test
  is a sizing *decision* and its effect on risk and edge, not price-time
  priority, which the base repo and the options extension already validate
  against the real matcher at smaller contract counts. "Quoted size" here
  is bookkeeping (a cap on how many lots can fill before the next requote),
  not a resting order with its own price-time rank.
- **The convex program is a linear program**, not a general convex
  program: the objective (expected edge, linear in quoted size) and every
  constraint (a Greek budget, linear in quoted size) are affine, which is
  what the resume's "one convex program" line means concretely and what
  lets CVXPY re-solve it in milliseconds, 20,000+ times across the full
  benchmark, using CVXPY `Parameter`s so only the numeric values change
  between solves, not the problem structure.
- **The risk budget is enforced against the worst case, not the expected
  case.** The LP bounds how much vega/gamma/delta the book *could* add if
  every quoted lot on the exposed side filled this interval, not how much
  it is expected to add; actual fills are far sparser (about one arrival
  per tick across all 120 contracts), so the realized excursion is usually
  well inside the worst-case bound the LP enforced. That gap, not a flaw,
  is why "inside budget" is measured well above 50% even though the LP's
  own guarantee is a one-sided worst case.
- **There is no hedging in this extension.** Unlike the options extension's
  delta-hedging, the risk budget here is held by *quoting* less on the
  exposed side, never by trading the underlying to flatten existing
  inventory; the budget constrains new exposure, it does not unwind old
  exposure. A book already past its budget (from a fill the LP did not
  control) can only stop making it worse, not make it better, until flow
  happens to trade it back down (see "The cap is computed, not optimized,
  when a budget is already breached" in Findings).
- **120 contracts, not 33.** The chain is 15 strikes x 8 expiries, a
  materially larger book than the options extension's 33, chosen because
  the point of this extension is a *book-level* allocation decision, which
  needs enough contracts for the LP's choice of which contracts to size up
  or down to be a real tradeoff, not an edge case.
- **Edge per quoted lot is a flat $0.02 (a 2-cent half spread) for every
  contract**, the same convention as this repo's `base_half_spread_ticks=2`
  default. The LP is therefore not trading off "wide spread, small size"
  against "tight spread, big size" (spread width is not a decision
  variable here); its only lever is how many lots to offer at that fixed
  edge per contract, which isolates the risk-budgeting decision from the
  widening decision the options extension already explores separately.

### The quoter: size skew, not price skew

The quoter's two levers on a stale book are the usual two: move the quoted
price, or change the quoted size. This project's flow model makes the first
lever a no-op (see "Honest framing"), so the inventory-skew policy only uses
the second: at each requote, `bid_size = clamp(base_size - skew_coef *
inventory, 0, 2*base_size)` and symmetrically for `ask_size`. A market maker
long inventory quotes less bid size (buys less, capping further
accumulation) and more ask size (sells more, encouraged to reduce the
position); the floor at zero means a side can be fully withdrawn, and any
taker that would have hit a withdrawn side is simply discarded by the book
rather than filled, exactly as a real market order with no resting
counterparty would be.

### The P&L identity

Let `inv_i` be inventory after event `i` (`inv_0 = 0`), `delta_i` the signed
quantity the quoter traded at event `i`, `price_i` the fill price, and `v_i`
the true fair value immediately after event `i`. Marking the session to
market at every step and telescoping the sum gives, exactly:

```
Total P&L = sum_i [ delta_i * (v_quote_i - price_i) ]       <- gross spread captured
          + sum_i [ delta_i * (v_i - v_quote_i) ]            <- edge informed flow took (negated: adverse cost)
          + sum_i [ inv_{i-1} * (v_i - v_{i-1}) ]             <- inventory carried through the random walk
```

where `v_quote_i` is the true fair value at the moment the quote that got
hit was posted. Because every fill happens exactly at `v_quote_i +/-
half_spread`, the first term collapses to `|delta_i| * half_spread`
("gross capture") regardless of policy; the second term is the informed
edge, reported as a cost with its sign flipped; the third is "inventory
mark". All quantities are integers (ticks, lots, cash), so the identity is
checked for *exact* equality, not within a tolerance -- see
`tests/pnl_identity_test.cpp`.

### Extension: options market making with delta hedging

The chain is 11 strikes (`underlying0 +/- 2.0` apart) x 3 expiries, each a
European call priced by `options_math.hpp`'s closed-form Black-Scholes,
quoted into its own vendored `IntrusiveBook` (33 books, 33 `OrderPool`s,
held in a `std::deque` because both types are deliberately non-copyable
and non-movable -- see "Findings" in the sibling matcher repo for why).
Every tick:

1. Pick a contract vega-weighted (higher-vega contracts trade more) and
   submit one taker order, informed or not, same logic as the base
   repo's single-asset flow model.
2. Step the underlying one tick of correlated GBM; every contract's theo
   price and Greeks move with it.
3. If the taker order filled: attribute edge captured (from the actually-
   resting bid/ask tick, see "The bid floor" below) and adverse selection
   (from the gap between the post-move theo and the quote's own stale
   center, exactly the base repo's mechanism, generalized to 33 assets).
4. Mark every contract's inventory to its own theo move this tick
   (whether or not it just traded), and mark the underlying hedge
   position to its own move.
5. Recompute portfolio delta (sum of each contract's position times its
   current delta, plus the underlying hedge position); if it exceeds
   `--hedge-band`, trade the underlying to flatten it, paying
   `--hedge-slippage` per share.

**The P&L identity (options).** The same telescoping argument as above
applies independently to each of the 33 contracts and once more to the
underlying hedge leg, then sums, because each is its own single-asset
ledger with its own fills (or, for the underlying, its own hedge trades)
and its own carry. Defining:

```
edge_captured      = sum over fills of the realized per-fill revenue
                      (center tick minus the resting bid tick, or the
                      resting ask tick minus the center tick)
adverse_selection  = sum over fills of -(delta * (theo_after - center_at_requote))
inventory_mark_i   = sum over every tick of inv_prev_i * (theo_after_i - theo_before_i)
underlying_carry   = sum over every tick of underlying_inv_prev * (S_after - S_before)
transaction_cost   = sum over hedge trades of |hedge_qty| * hedge_slippage
hedge_slippage     = transaction_cost - sum_i(inventory_mark_i) - underlying_carry
```

`pnl_decomposed = edge_captured - adverse_selection - hedge_slippage` equals
`pnl_oracle = cash + mark-to-market of every contract and the underlying
hedge position` exactly (to floating-point tolerance): hedging exists
specifically to control the carry that `hedge_slippage` absorbs, so
folding both the real transaction cost and the residual tracking P&L into
one "cost of hedging" bucket is not a simplification, it is the standard
real-world definition of that number. `tests/options_pnl_identity_test.cpp`
sweeps hedge bands, widening settings, and informed-flow rates and asserts
the two sides agree to within `1e-6` of the session's own P&L magnitude.

**The bid floor.** A near-worthless deep-out-of-the-money contract's theo
price can round to as little as 1 cent; `max(1, center_tick - half_spread_tick)`
keeps the quoted bid at or above 1 cent rather than letting it go to 0 or
negative, which the book would reject. When that floor binds, the realized
bid-side spread is narrower than the nominal `half_spread`, so
`edge_captured` is computed from the contract's own actually-resting
`bid_px_ticks`/`ask_px_ticks`, not from the nominal spread -- see Findings
for the version that used the nominal spread and what it cost the identity.

### Extension: per-fill post-trade attribution

The base simulation already proves one P&L identity at the session level;
this extension proves the same identity holds when the three terms are
attributed fill by fill instead of summed once at the end, and adds the
one post-trade metric a session-level view cannot answer at all: how did
fair value move *after* each individual fill.

**Attributing `spread_captured` and `adverse_selection`.** Both are
already per-event quantities inside `SessionRunner::run`'s loop (`qty *
half_spread` and `-(delta * (v_after_jump - center_at_requote))`); the
extension's only change here is writing them into a `FillRecord` instead
of only adding them into the session's running totals.

**Attributing `inventory_mark`.** This term is different: it accrues
every tick, whether or not a fill happens that tick, because it is the
cost (or benefit) of *carrying* whatever inventory is currently on the
book. The extension attributes each tick's carry to the most recent fill,
tracked as `last_fill_idx` while the session runs: a tick's carry uses
`inv_prev`, the inventory level set by that most recent fill, so crediting
the carry to that same fill keeps the attribution mechanically exact
rather than approximate. The one subtlety is ordering: on a tick that
itself contains a new fill, that tick's carry (computed from `inv_prev`,
*before* the new fill) is credited to the *previous* fill, and only the
*next* fill's `inv_before` reflects the position the new fill just
created. Before any fill has happened, `inv` is still exactly 0, so the
carry is 0 and has nowhere to go; the code skips attributing it rather
than attributing a true zero to a fill that does not exist yet.

**Markouts.** `vpath`, the fair value immediately after each tick's jump,
is collected once per session (only when a caller asks for the per-fill
ledger, so the no-argument call path pays nothing extra). After the
session loop finishes, each fill looks up `vpath` at `tick + 1`, `tick +
10` and `tick + 60`, clamping to the last tick and flagging when it does.
Measuring from `fill_price` rather than from fair value at the fill
(`v_quote`) means the half spread the market maker captured is baked into
the markout number from the first tick onward; see Findings for what that
implies about reading the measured numbers.

### Extension: Python strategy interface

The two built-in policies (`FixedSize`, `InventorySkew`) are both one
`if` branch inside `requote`'s lambda in `session_runner.hpp`. This
extension adds a third: `Policy::External`, which calls
`SessionParams::external_quote_fn(inv, base_size, skew_coef, cap,
bid_size, ask_size)` instead, and otherwise changes nothing about the
session loop. That is the whole surface a Python policy needs: the
decision is a pure function of the current inventory and three fixed
parameters, called once per requote, with no other state leaking across
the C++/Python boundary.

`python/pymm/binding.cpp` (nanobind) exposes three functions over this
hook:

- `run_native_inventory_skew(...)`: runs `Policy::InventorySkew` directly,
  no Python involved. The baseline both other functions are compared
  against.
- `run_with_python_policy(..., policy_fn)`: runs `Policy::External` with
  `external_quote_fn` wired to call the Python callable `policy_fn` and
  translate its `(bid_size, ask_size)` tuple back into the two output
  references the hook expects.
- `benchmark_policy_calls(policy_fn, n_calls)`: calls `policy_fn` back to
  back `n_calls` times in a tight C++ loop, timed with `std::chrono`
  inside the extension module (not from Python), to isolate the cost of
  one Python round trip from the rest of a session's own cost. See
  "Measured results (Python strategy interface)" for why this, not the
  whole-session timing difference, is the number reported as the cost
  per decision.

`tests/external_policy_test.cpp` proves the hook itself is lossless in
pure C++ first: a C++ lambda implementing the exact same clamp formula as
`InventorySkew`, run through `Policy::External`, reproduces
`InventorySkew`'s session P&L bit-for-bit across a 5x3x30 sweep of
informed-flow rates, spreads and seeds. `python/tests/test_pymm.py` then
proves the Python half: the same formula, now a real Python function
called through nanobind, reproduces the native path exactly too, and a
negative control (a deliberately different Python policy) proves the
match is not a hook that silently ignores whatever Python returns.

### Extension: risk-budgeted quote optimization across a 120-contract book

Every `requote_interval` ticks, for each policy:

1. **`contract_by_contract`** resets every one of the 120 contracts' bid
   and ask size to `max_size` (10 lots), independent of every other
   contract and of the book's current inventory. This is the uncoordinated
   baseline: each contract's quote decision uses no information about the
   rest of the book, which is what "quoting contract by contract" means
   literally.
2. **`book_optimized`** computes the book's current net vega, gamma and
   delta (`sum_c inv_c * greek_c`), computes how much headroom is left on
   each side of each Greek before its budget would breach in the worst
   case (`BookOptimizer._cap`, in plain Python, not inside the LP: see
   "Findings" for why a budget already breached must still produce a
   feasible, not infeasible, program), and solves the LP in
   `optimizer.BookOptimizer`:

```
maximize    sum_c edge_c * (bid_c + ask_c)
subject to  vega_c . bid  <= bid_cap_vega     vega_c . ask  <= ask_cap_vega
            gamma_c . bid <= bid_cap_gamma    gamma_c . ask <= ask_cap_gamma
            delta_c . bid <= bid_cap_delta    delta_c . ask <= ask_cap_delta
            0 <= bid_c, ask_c <= max_size      for every contract c
```

Between requotes, flow arrives exactly as in the options extension: one
taker order per tick, picked vega-weighted across the 120 contracts,
informed with probability `informed_frac` and exploiting the gap between
the current theo and the quote's stale center when that gap is nonzero.
If the policy's quoted size on the needed side is still positive, the
order fills (edge captured, size decremented, inventory updated); if the
size has already been quoted down to zero, by design in `book_optimized`
or exhausted in either policy, the order is declined and no fill happens.
`ticks_in_vega_budget` (and the gamma/delta equivalents) are then measured
every tick, against the *realized* net Greeks after that tick's fill and
the underlying's move, not against the LP's own worst-case bound.

**Why the LP's caps are computed outside CVXPY, not inside it.** An
earlier version wrote the constraint directly as `vega . bid <= budget -
net_vega0` with `net_vega0` a CVXPY `Parameter`. That is fine while
`net_vega0 <= budget`, but the moment the book has already drifted past
budget (which happens, because the LP controls future quoting, not past
fills), the right-hand side goes negative and the LP becomes infeasible,
exactly the tick a risk-aware quoter most needs an answer. Computing
`bid_cap = max(budget - net_vega0, 0.0)` in plain Python before the solve
keeps the program feasible (0 lots is always within bounds) in every
case, including a book already past budget, where `book_optimized`
correctly responds by zeroing the vega-increasing side while still
leaving the vega-decreasing side open to trade back toward budget.

## Findings

**The first informed-flow definition understated adverse selection by
roughly 10x, and the bug was in when informed flow was allowed to act, not
in the P&L math.** The first implementation let an informed trader exploit
a fair-value jump only on the exact tick the jump landed: `is_informed &&
jump_happens`. That is a 1-tick-wide window, and it produced an
adverse-selection give-back of 0.31% of gross capture at 20% informed
participation, barely distinguishable from the expected value under random
flow. The P&L identity held exactly in this version too, which is the
trap: a wrong *model* can still be an internally consistent one, and the
reference-oracle diff that checks arithmetic cannot catch a modeling error
in what the arithmetic is fed. The giveaway was domain reasoning, not a
test failure: a quote posted at the last requote stays stale for the entire
interval until the next requote, not for one tick, so an informed trader
who already knows the current fair value should be able to exploit that gap
on *any* tick before the next requote, not only the tick a jump happened to
land on. Redefining the exploit condition as `gap = v - center_at_requote;
is_informed && gap != 0` raised the measured give-back to 2.03% under the
original parameters, and to 4.34% after also widening the requote interval
(see Measured Results) -- a real, mechanical, order-of-magnitude fix, not a
curve-fit to a target number.

**Size-skew with a tight clamp relative to typical inventory swings produced
an extreme, not a proportionate, variance reduction.** The first skew
parameters (`base_size=10`, `skew_coef=1`) zeroed one side's quoted size
whenever `|inventory| >= 10`, which the fixed-size policy's own inventory
regularly exceeds (stdev around 30), so the skewed policy spent much of
each session fully withdrawn from one side. That cut inventory stdev by
13x, a far larger effect than the resume bullet's 3.1x, at a smaller gross
capture cost (4.1%) than its 9%. Tripling `base_size` to 30 made the clamp
bind less often relative to the same inventory swings, producing a more
graduated throttle: a 4.77x stdev cut at a 2.94% capture cost, reported
below as the final measured numbers for both claims.

**The options P&L identity broke by $0.01 to over $1 per session on the
first attempt, and the bug was discretization, not arithmetic.** The
first implementation used the continuous Black-Scholes price for
`center_at_requote` and the "theo before/after" carried into inventory
mark, while the book itself only ever trades at a rounded integer cent.
That fractional-cent gap compounds over thousands of fills and ticks into
a real, visible identity failure (not floating-point noise: the gap scaled
with spread width, from about $0.01-$0.2 per 500-tick session at a 2-cent
half spread to over $1 once vega-scaled widening made the gap wider).
The fix was to quantize every price that feeds the identity (`quantize()`
in `options_session_runner.hpp`) to the exact same integer-cent grid
`detail::to_ticks()` uses to place the order, so a theo price used for
bookkeeping is never rounded differently than the price used to trade it.
Greeks stay continuous on purpose, since they only drive decisions (the
hedge trigger, the widening amount), never a cash flow.

**A second, smaller version of the same class of bug: the bid-price floor.**
Even after quantizing, `edge_captured` was first computed as
`qty * half_spread_dollars[idx]`, the *nominal* half spread, which is
wrong exactly when `max(1, center_tick - half_spread_tick)` floors a
near-worthless contract's bid at 1 cent instead of letting it go negative.
The fix was to compute `edge_captured` from the contract's own
actually-resting `bid_px_ticks`/`ask_px_ticks` (see "The bid floor" in
Architecture), which is exact regardless of whether the floor bound.

**Vega-scaled widening cannot reduce the dollar cost of adverse selection
here, only dilute it as a share of a larger spread revenue, and that is a
real finding, not a workaround.** Because taker flow is price-insensitive
by design (the same simplification the base repo's price-skew finding
already disclosed: a market order crosses whatever is resting regardless
of its price), `adverse_selection` measured bit-for-bit identical between
a flat-spread run and a vega-scaled run at the same base spread and seed
(both $77,919.90 over 500 sessions in the final comparison below) --
informed flow still trades exactly as much, exactly when it chooses to.
Widening only grows `edge_captured`, which shrinks the *ratio*
`adverse_selection / edge_captured`. That ratio is exactly what the resume
bullet measures ("cut edge lost to informed flow from X% to Y%"), and
diluting a fixed cost against a larger revenue base is a real market-
making lever, not an artifact of this simulation.

**The widening effect is invisible below about a 1-tick rounding
threshold, which is itself worth stating plainly.** A first attempt at a
15% vega-scaled widening coefficient on a 2-cent base half spread produced
*zero measured change*: `detail::to_ticks()` rounded the widened spread to
the same integer cent as the unwidened one for nearly every contract, so
the two runs traded at bit-identical prices. The second and third attempts
widened the base half spread to 10 and then 35 cents (so a given
percentage widening crosses an integer-cent boundary) and raised the
widening coefficient, which is what let the 11.27%-to-4.16% result below
actually be measured rather than rounded away.

**The hedge-band/hedge-cost tradeoff is real and was swept, not hit on the
first try.** A 0.10-share band (closest to the resume's literal number)
hedges on almost every fill and measured a 53.4% cost of gross edge; a
1.0-share band still measured 27.6%. Both numbers are honestly reported in
`docs/options_benchmark_output.txt`'s predecessors (not committed; the
final sweep is), but neither is the number below. A 3.0-share band with
$0.01/share slippage is the third and final attempt, landing at 6.24% cost
against the resume's 8.5%, still cutting end-of-session P&L variance 5.96x
against the resume's 3.8x. The honest reading is that this project's
flow model (one taker order per tick, vega-weighted across 33 contracts)
makes delta accumulate in large, infrequent jumps rather than smoothly, so
there is no band width that is simultaneously "tight" by the resume's
number and "cheap" by the resume's number; three genuine attempts moved
the cost from 53% to 6%, and the variance cut stayed well above the
claimed cut throughout.

**Markout, measured from the actual fill price, is dominated by the spread
captured, and that is expected, not a flaw in the metric.** The first
measurement (below) showed uninformed fills averaging a markout within
noise of the 2-tick half spread, and informed fills averaging well below
it, never negative. That is the correct behavior for this definition: a
fill's markout starts at (roughly) `+half_spread` purely from the spread
captured, and informed flow's exploited gap only erodes that baseline, it
does not independently drag the number negative in this model, because the
jump that creates the exploitable gap is itself bounded (one tick, one
direction) relative to a 2-tick spread. A reader who wants a markout metric
that isolates adverse selection with zero spread contribution baked in
would instead measure from `v_quote`, not from `fill_price`; both are
documented explicitly above so neither is mistaken for the other.

**The whole-session timing difference between the native and Python-
policy paths is too noisy on this shared machine to be the per-decision
number, and measuring it anyway was the first attempt.** The design
intent was "time 500 native sessions, time 500 Python-policy sessions,
divide the difference by the number of decisions". The first measurement
did exactly that and the difference came out negative on more than one
run (the Python-policy path measuring *faster* than native): the policy
fires only once every 60 ticks, so its cost is a small fraction of a
~550us session dominated by order-book matching, well inside this
machine's run-to-run scheduling noise (see "Resource courtesy" in the
playbook this repo follows). The fix was not a bigger sweep; it was
measuring the right thing. `benchmark_policy_calls` isolates exactly the
Python round trip, timed with `std::chrono` inside the C++ extension, in
a loop with no session logic around it at all, and that number is stable
across repeated runs (0.270-0.276us in three consecutive runs) in a way
the whole-session difference is not. Both numbers are reported below;
only the isolated one is the per-decision claim.

**The isolated per-decision cost measured well under the 12us design
target, not over it, which is the opposite direction of most shortfalls
elsewhere in this README.** A nanobind round trip for a function this
small (four integer arguments in, a two-integer tuple out) costs a few
hundred nanoseconds on this machine, not microseconds; reported as
measured, in both directions, the same discipline this README applies to
every other number.

**A budget sentinel of 1e9, meant to mean "effectively unreachable", made
CLARABEL misreport a trivially bounded LP as unbounded.** The first version
of `test_unreachable_budget_matches_uncoordinated_baseline` set every
budget to `1e9` and expected `book_optimized` to reproduce the
uncoordinated baseline exactly, since a cap that large should never bind.
It did not: on one tick out of 300, the solve returned status `unbounded`
and zeroed every quoted size, even though `bid <= max_size` and
`ask <= max_size` trivially bound the problem regardless of the other
constraints. The cause was scale, not logic: a right-hand side around 1e9
against decision variables around 10 and coefficients around 1-13 is
numerically unbalanced enough that CLARABEL's own scaling heuristic lost
track of the box constraint on at least one solve. The fix was not a
solver flag; it was recognizing that "unreachable" does not require "as
large as a float can represent" -- clipping every computed cap to `1e6`
(`optimizer._CAP_CEILING`) is still nine orders of magnitude past any
budget this extension actually measures with, and the solver has not
misreported a status since. This is the kind of bug a reference-oracle
diff against a *different* solver (`reference_oracle.solve_lp_scipy`)
would also not have caught by itself, since the independent SciPy/HiGHS
check was run at realistic budget magnitudes, not at the degenerate
sentinel value; the invariant test that caught it
(`test_unreachable_budget_matches_uncoordinated_baseline`) is the one
that mattered here, not the oracle diff.

**Three genuine attempts at the budget magnitudes themselves, and the
honest result is that holding net vega inside budget 98.6% of the time at
a 4.1% edge cost is not what this flow model produces at any budget level
tried.** The first attempt (`vega=150, gamma=1.5, delta=10`, chosen as
roughly 2x the one-sided vega/gamma/delta a single near-term, near-the-
money contract would add at `max_size`) measured the uncoordinated
baseline inside its own vega budget only 51.80% of the time, well under
the resume's 71.2% for the baseline to begin with. The second attempt
loosened the vega budget to 220 (chosen from the measured distribution of
the baseline's own net vega, not reverse-engineered to hit 71.2% exactly)
and brought the baseline to 68.67%, close to the resume's number, while
`book_optimized` reached 96.73% at a 15.14% edge cost. The third attempt
loosened the gamma and delta budgets further (10 and 60) to check whether
they, not the vega budget, were driving the edge cost; the cost barely
moved (15.07%), which is itself the finding: at this flow model's
arrival rate and contract count, tightening the vega budget enough to
hold it above 95% of the time costs roughly 15% of gross edge, not 4.1%,
because the LP's only lever to defend a tight budget is to decline fills
outright on the exposed side, and declining fills is exactly what the
edge-cost number measures. The direction of both numbers (higher
in-budget percentage, higher edge cost than the uncoordinated baseline)
is correct and mechanically understood; the specific magnitudes are not,
and are reported as measured, not re-targeted further, per the
measurement rule this project is built under.

## Sibling comparison

The matching core is reused unchanged from
[`lock-free-order-matching-engine`](https://github.com/Manas103/lock-free-order-matching-engine)
(5.03M orders/sec at 1 gateway in that repo's own throughput benchmark; this
project never touches that path, since a market-making session submits one
order at a time from a single thread and is not a throughput exercise).
What that repo validates once (price-time priority, O(1) cancel/amend,
exact conservation of submitted quantity) this project inherits for free and
spends its own validation budget on the part that is new: the flow model
and the P&L accounting around it.

The options extension deliberately does not vendor
[`options-pricing-greeks-engine`](https://github.com/Manas103/options-pricing-greeks-engine)'s
pricer. That repo's own validated path is a variance-reduced Monte Carlo
cross-checked against closed-form Black-Scholes, built for pricing
accuracy under a slow reference; this project needs the closed form itself
evaluated tens of millions of times per batch (33 contracts x 4000 ticks x
500 sessions x 2-3 passes per tick), where a Monte Carlo pricer would make
the sweep in Measured Results impractical. Re-deriving the two formulas
`options_math.hpp` needs and cross-checking them against a fresh,
independent Monte Carlo (the slow path, run once per test case rather than
once per simulated tick) is the design that is actually faster to validate
here, not a case of a good existing repo losing to a worse new one.

## Limitations

- The fair value process is exogenous and does not react to the quoter's
  own trades; a richer model would let aggregate order flow move the
  "true" value, which this project does not attempt.
- Neither informed nor uninformed flow is price-sensitive: arrivals and
  side choice do not depend on how good the quoted price is, only the
  informed trader's knowledge of the value gap. Price-based skewing is
  therefore a measured no-op here by construction, not a finding about
  price skewing in general.
- Order size is fixed at 1 lot per taker; the quoter's own size is the only
  size that varies (under the skew policy).
- 20% informed participation and the other session parameters are fixed at
  the values stated in Measured Results; the three claimed numbers were
  not independently re-targeted after the final parameter choice (see
  Findings for the attempts that were made and why they stopped).
- The risk-budgeted optimization extension does not route orders through
  the vendored matching engine (see "Honest framing"); "quoted size" there
  is a bookkeeping cap, not a resting limit order with its own price-time
  rank. It is also the one C++20 repo extension in this project written
  entirely in Python; the "C++20" in this project's stack line refers to
  the base simulation and the two earlier extensions it reuses the flow
  model from, not to this one.
- The risk budget is a worst-case, one-interval bound with no hedging
  mechanism to unwind inventory already on the book; a budget already
  breached can only be prevented from growing, not actively reduced, by
  this extension's LP (see "Honest framing").
- The edge-per-lot the LP optimizes is a flat constant across all 120
  contracts; the optimizer is therefore purely a risk-allocation decision
  (which contracts to size down), not a joint spread-width-and-size
  decision, which the options extension's vega-scaled widening already
  explores on a separate axis.
- The options extension inherits all of the above (exogenous underlying,
  price-insensitive flow) and adds its own: calls only, no puts; risk-free
  rate 0; one `sigma` for both the simulated underlying and the quoter's
  own theoretical value, so there is no modeled vol-estimation edge,
  only the staleness edge the base repo already has, carried into Greek
  space; a hedge trade is an assumed underlying fill at mid plus a fixed
  slippage, not matched against a second book; quote size is fixed per
  contract, so delta hedging against the underlying is the only inventory
  lever this extension models (no options analogue of the base repo's
  size-skew policy).
- Because taker flow is price-insensitive, vega-scaled widening cannot
  reduce the dollar cost of adverse selection, only dilute it as a share
  of a larger spread revenue (see Findings); a reader should not infer
  that widening the spread deters informed flow in this model, because by
  construction it cannot.
- No single hedge-band width tried landed inside the resume's claimed
  range for both the variance-cut and the cost-of-hedging numbers at
  once; the final parameters (band 3.0 shares, $0.01/share slippage) are
  the closest of three genuine attempts on the cost number, reported as
  measured, not the literal 0.10-share band the resume bullet names.
- **The per-fill attribution extension inherits every limitation of the
  base simulation above** (exogenous fair value, price-insensitive flow,
  fixed-size takers), plus its own: carrying `inventory_mark` entirely to
  the most recent fill is one defensible attribution convention, not the
  only one, and a reader who wants a time-weighted carry split would need
  to change that rule; markout is measured from the actual fill price, so
  it is not a clean, zero-baseline adverse-selection metric by itself (use
  the existing `adverse_cost`/`adverse_selection` fields for that); "1 tick
  = 1 second" for the markout horizons is a stated unit convention, not a
  measured wall-clock correspondence; and the per-fill CSV `run_attribution`
  produces (1.86M rows for 500 sessions) is not committed, only the raw
  DuckDB summary is, because of its size.
- **The Python strategy interface only exercises the single-asset
  `SessionRunner`'s `InventorySkew` policy, not the 33-contract options
  session.** `OptionsSessionRunner` has no `Policy::External` hook; a
  Python strategy for the options book would need the same change
  applied there, which this extension does not do. The Python callable
  also only decides bid/ask *size*; it cannot change the quoted *price*,
  the requote cadence, or anything else about the session loop, because
  `external_quote_fn`'s signature is exactly as wide as `InventorySkew`'s
  own decision and no wider. The isolated per-decision benchmark measures
  one specific call shape (four integers in, a two-integer tuple out); a
  policy that received or returned a larger payload (e.g. a full order
  book snapshot) would almost certainly cost more than the 0.270us
  measured here, and that case is not benchmarked.
